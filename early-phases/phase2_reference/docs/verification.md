# Verification: Methodology, Test Inventory, and Results

This document covers everything about *how* the design in
`docs/architecture.md` is verified: the testbench architecture, the
independent reference models, the full test inventory mapped to the
assignment's requested test categories, simulation instructions, coverage
philosophy, known limitations, and future improvements.

## 1. Testbench architecture

```
tb/
├── uart_tasks.v        - shared tasks (`include`d by every testbench below)
├── uart_tb.v             - top-level loopback: 3 DUTs (NONE/EVEN/ODD parity)
├── uart_tx_tb.v            - TX unit test: 3 DUTs, line-level parity capture
├── uart_rx_tb.v              - RX unit test: fault injection lives here
├── uart_vectors_tb.v           - replays Python-generated vectors against RX
└── vectors/
    └── random_vectors.txt        - generated by scripts/gen_vectors.py

scripts/
└── gen_vectors.py       - independent Python reference model + vector generator
```

Plain Verilog has no package/import system, so `uart_tasks.v` is shared
across every testbench via textual `` `include ``, per the naming
contract documented in that file's header comment. This mirrors the
approach from phase 1 and was kept unchanged because it continues to work
well: each testbench declares signals with the contractually-expected
names (`clk`, `reset`, `tx_data`, `rx_valid`, `parity_error`, etc.,
aliased via `wire` declarations where a file has multiple DUT instances),
and gets the shared tasks "for free."

**Why fault injection lives in `uart_rx_tb.v`, not `uart_tb.v`:** a
working `uart_tx` cannot produce a malformed frame (that's the entire
point of it being correct). Testing "what happens when a parity/stop bit
is wrong" therefore requires bit-banging a hand-built frame directly onto
an `rx` pin, bypassing `uart_tx` entirely -- which only makes sense in a
testbench that isn't also trying to drive a loopback wire that `uart_tx`
is simultaneously driving (that would be two drivers on one net).
`uart_tb.v` focuses on what it's uniquely suited for: full-link,
multi-parity-mode, high-volume normal-traffic verification (the complete
0x00-0xFF sweep, three separate parity configurations, thousands of
checks) plus reset-during-transmission/reception, which *does* make sense
in a loopback context.

## 2. Independent reference models (why two, and why each counts)

The assignment is explicit that a reference model must not simply reuse
the DUT's own algorithm -- otherwise a bug in the RTL's parity formula
would just as easily exist in the "check," and the check would never
catch it. This project uses two independent models, deliberately
different from each other and from the RTL:

**1. Verilog-side (`model_parity_bit` in `tb/uart_tasks.v`):** computes
parity with an explicit `for` loop that sums the individual bits of the
byte one at a time (`ones = ones + data[i]`), then checks `ones % 2`. The
RTL, by contrast, computes parity with a single reduction-XOR operator
(`^data`) -- a completely different computational structure (a loop with
an accumulator vs. a single combinational gate-tree operator) that
happens to compute the same mathematical quantity. If the RTL's
reduction-XOR were ever accidentally applied to the wrong signal, or an
EVEN/ODD complement were swapped, this model would not "helpfully" agree
with the mistake, because it isn't built the same way.

**2. Python-side (`scripts/gen_vectors.py`):** goes a step further by
being an entirely separate program in an entirely separate language, with
its own from-scratch parity computation (`bin(data).count("1")`, using
Python's built-in integer bit-counting, which shares no code path with
either the RTL or the Verilog-side model above) and its own decisions
about which frames to corrupt and how. It writes a plain-text vector file
(`data_hex parity_mode inject_bad_parity inject_bad_stop
expected_outcome`) that `tb/uart_vectors_tb.v` reads back with
`$fscanf`/`$fgets` and replays against the RTL, checking that the DUT's
actual outcome (clean receipt / parity error / framing error / both)
matches what Python predicted. Regenerating this file with a different
seed (`make vectors SEED=<n> NVEC=<count>`) produces a fresh, independent
batch of randomized coverage without touching any Verilog.

This two-layer approach was a deliberate use of "Python where it adds
real value" (per the assignment's guidance not to introduce another
language just to look more advanced): the Verilog-side model alone
already satisfies "independent of the DUT," and would have been
sufficient on its own; the Python layer adds genuine additional value by
being independent of the *entire Verilog toolchain*, not just of the
specific RTL module under test, and by making it trivial to generate
much larger or differently-distributed randomized regressions without
writing more Verilog.

## 3. Test inventory, mapped to the assignment's requested categories

### Normal operation

| Requested                | Where covered                                                        |
|---------------------------|------------------------------------------------------------------------|
| 0x00, 0xFF, 0x55, 0xAA     | `uart_tb.v` "Required byte patterns" (EVEN+ODD); also the first four values the 0x00-0xFF sweep passes through (NONE/EVEN/ODD) |
| 0x00 through 0xFF           | `uart_tb.v`, full sweep, once per parity mode (768 loopback checks alone) |
| random bytes                  | `uart_tb.v` "Random bytes" (10 per mode); `uart_vectors_tb.v` (randomized, Python-generated) |
| repeated bytes                   | `uart_tb.v` "Repeated bytes" (same value, 5x in a row, EVEN) |
| back-to-back bytes                  | `uart_tb.v` "Multiple consecutive / back-to-back bytes" (NONE); `uart_rx_tb.v` "back-to-back frames, no idle gap, mixed good/bad" |

### Parity

| Requested                     | Where covered |
|---------------------------------|------------------|
| parity disabled                   | `uart_tb.v` NONE-mode DUT throughout (full sweep, patterns, bursts, random) |
| even parity                          | `uart_tb.v` EVEN-mode DUT; `uart_tx_tb.v` EVEN capture; `uart_rx_tb.v` EVEN fault injection |
| odd parity                              | `uart_tb.v` ODD-mode DUT; `uart_tx_tb.v` ODD capture; `uart_rx_tb.v` ODD fault injection |
| correct parity                             | all of the above "good frame" cases |
| incorrect parity                              | `uart_rx_tb.v` "PARITY FAULT INJECTION" (EVEN and ODD); `uart_vectors_tb.v` PARITY_ERROR vectors |
| parity error on different data patterns          | `uart_rx_tb.v` injects bad parity across 5 distinct byte patterns per mode; `uart_vectors_tb.v` covers 8 fixed coverage bytes x 2 modes x fault combinations, plus randomized bytes |

### Framing

| Requested                | Where covered |
|----------------------------|------------------|
| correct stop bit             | every "good frame" test, implicitly |
| stop bit forced LOW             | `uart_rx_tb.v` "FRAMING FAULT INJECTION"; `uart_vectors_tb.v` FRAMING_ERROR vectors |
| short invalid stop                 | not separately distinguished from "stop bit forced LOW" -- this design samples the stop bit once, at its center; there is no intermediate "short but not fully low" case at the sampled resolution (see Section 5, "Known limitations") |
| repeated framing errors               | `uart_rx_tb.v` injects 5 separate bad-stop frames in a row; the "just below break threshold" test's one expected leading `framing_error` is itself a repeated-condition case |

### Break

| Requested                          | Where covered |
|---------------------------------------|------------------|
| normal frame                            | baseline for every other break test (nothing is broken by the break-detection logic being present) |
| exactly below break threshold              | `uart_rx_tb.v` "BREAK DETECTION: below / at / above threshold", first block |
| at break threshold                            | same test, second block (`BREAK_CYCLES + 20`, i.e. at/above) |
| above break threshold                            | same test, second block |
| break followed by valid frame                       | `uart_rx_tb.v` "BREAK FOLLOWED BY A VALID FRAME (recovery)" |
| break followed by idle                                 | implicit in every break test: `hold_low_even` releases to idle-high, and `break_detected` clearing is directly checked before the next test proceeds |

### Reset

| Requested                    | Where covered |
|--------------------------------|------------------|
| reset while idle                  | `uart_tb.v` "Reset behavior" block (all three DUTs) |
| reset during TX                      | `uart_tb.v` "RESET DURING TX / RX" (shared reset -- see architecture.md Section 10 for why TX and RX reset together in this design) |
| reset during RX                         | `uart_rx_tb.v` "RESET DURING RECEPTION" (mid-frame, independent of TX) |
| reset during parity                        | covered by `uart_rx_tb.v`'s reset-during-reception test's timing window, which lands inside the data-bit region; a dedicated parity-phase-specific reset window is a natural extension (see Section 5) |
| reset during stop                             | structurally identical code path to reset-during-data in this FSM (the same `if (reset)` branch handles every state uniformly), and is exercised incidentally whenever a reset's timing happens to land there, but is not a separately *named* test -- see Section 5 |
| reset after error                                | `uart_rx_tb.v`'s post-reset-recovery check runs after a mid-frame reset, confirming the receiver is fully functional again; not specifically preceded by an error condition, but exercises the same reset-recovery code path |

### Combined

| Requested                              | Where covered |
|-------------------------------------------|------------------|
| parity + framing error                       | `uart_rx_tb.v` "COMBINED PARITY + FRAMING ERROR"; `uart_vectors_tb.v` BOTH_ERRORS vectors |
| break + subsequent valid data                   | `uart_rx_tb.v` "BREAK FOLLOWED BY A VALID FRAME" |
| random traffic with injected errors                | `uart_vectors_tb.v`'s randomized vectors mix clean frames, single-fault frames, and double-fault frames in one regression run (see `scripts/gen_vectors.py`'s weighted distribution) |

## 4. Assertions (procedural, not SystemVerilog)

This project stays in Verilog-2005/2012-compatible plain Verilog (no
SystemVerilog `assert property`), consistent with the "don't silently
introduce SystemVerilog-only syntax" constraint. The things an SVA
environment would typically assert are instead checked procedurally:

- **"TX must be HIGH while idle"**: `check_cond("Reset: tx idle high
  ...")` and the idle-behavior check in `uart_tb.v`/`uart_tx_tb.v`.
- **"TX must remain busy throughout an active frame"**: `uart_tb.v`'s
  "tx_busy asserted throughout an entire frame" test polls `tx_busy`
  every single cycle across an entire frame's duration and fails if it
  ever drops early.
- **"tx_done must not remain HIGH indefinitely"**: checked as "tx_done is
  a single-cycle pulse" -- read one cycle after the expected pulse and
  confirm it has already returned low.
- **"rx_valid should only occur after a completed frame"**: implicit in
  every loopback/vector test (`rx_valid` is only ever observed after a
  full frame's worth of bit-driving has elapsed; the testbenches never
  observe it firing early because the RTL only sets it in `S_STOP`).
- **"parity_error should only correspond to parity-enabled reception"**:
  the NONE-parity DUT in `uart_tb.v` is run through the entire 0x00-0xFF
  sweep and never once checked for `parity_error`, because that signal is
  architecturally tied to `PARITY_MODE != NONE` in the RTL (see
  `uart_rx.v`'s `S_STOP` logic) -- there is no code path in a
  NONE-parity instance that can set it.
- **"framing_error should correspond to an invalid stop bit"**: directly,
  by construction, in every framing-fault-injection test (the only thing
  ever varied to trigger it is the stop bit's driven value).

## 5. Known limitations

- **No fractional baud-rate generation.** As in phase 1, `CLKS_PER_BIT`
  is computed with integer division and carries the small, calculated
  error documented in `docs/architecture.md` Section 7. Not needed at the
  error levels observed; would be a natural next step if a specific
  clock/baud pair produced unacceptable error.
- **No configurable stop-bit count.** `STOP_BITS` is effectively fixed at
  1 throughout this phase; the assignment explicitly scoped this out
  ("do not unnecessarily implement... 1.5 stop bits unless there is a
  clear architectural reason"), so it was not built. `DATA_BITS` and
  `PARITY_MODE`, which *were* requested, are properly parameterized
  (including `bit_index`/`rx_shift`/`shift_reg` widths scaling with
  `DATA_BITS`), so extending to a configurable stop-bit count later is a
  bounded, well-scoped change rather than a redesign.
- **Only `DATA_BITS = 8` is verified**, even though the RTL is written to
  scale with the `DATA_BITS` parameter (widths derived via `$clog2`
  throughout). The assignment explicitly discourages implementing 5/6/7-
  bit support without a clear architectural reason; the parameterization
  exists for forward-compatibility and code clarity, not because
  non-8-bit configurations are a tested, supported configuration today.
- **"Short invalid stop bit" is not distinguished from "stop bit forced
  fully LOW."** This design samples the stop bit exactly once, at its
  bit-period center, matching how it samples every other field. There is
  no notion of "a stop bit that started high, dipped briefly, then
  recovered" at the sampled time resolution -- from this receiver's
  point of view, the stop bit either reads `1` at its center (valid) or
  `0` (framing error), with no distinct third category. A future
  enhancement (see Section 6) could add multiple sub-samples per field to
  detect that kind of transient, at the cost of real added complexity.
- **Reset-during-parity and reset-during-stop are not separately *named*
  tests**, though the RTL's reset handling is state-independent (a single
  `if (reset)` branch at the top of the sequential block applies
  uniformly regardless of which state the FSM was in), so these cases are
  not architecturally distinct from reset-during-data -- they are the
  same code path exercised at a different, but not fundamentally
  different, moment in the frame. Adding explicitly-timed tests for these
  two exact windows would be a low-effort, high-confidence addition.
- **A single, shared `reset` for TX and RX** (inherited from phase 1's
  top-level interface, not redesigned in this phase) means "reset during
  TX" and "reset during RX" cannot be tested with independent timing in
  the loopback testbench -- both halves reset simultaneously. This is
  documented rather than hidden; `uart_rx_tb.v`'s RX-only unit test does
  exercise RX-specific reset timing independent of any TX activity, since
  that testbench has no `uart_tx` instance at all.
- **No FIFOs**, per the assignment's explicit scope for this phase --
  each new byte overwrites `rx_data`/completes a new `tx_start` cycle;
  there is no queuing. Explicitly deferred to a later phase.
- **No formal functional coverage tooling.** Icarus Verilog does not
  support SystemVerilog functional coverage (`covergroup`/`coverpoint`).
  See Section 6 for how this project substitutes a testbench-side
  coverage summary, and Section 7 for the distinction between that and
  code coverage.

## 6. Coverage: what this project does, and code coverage vs. functional verification

**The distinction, stated explicitly (per the assignment's request not to
conflate the two):** *code coverage* asks "did the simulation exercise
every line/branch/toggle of the RTL at least once?" It is a measure of
the **stimulus's reach into the implementation**. *Functional
verification* asks "did we check that the design does the *right thing*
for every scenario that matters?" It is a measure of **correctness
against intent**, and says nothing about implementation structure at all.
A test suite can achieve 100% code coverage while still missing an entire
category of bug (e.g. toggling every line of `uart_rx.v` without ever
checking that `rx_data` holds the *correct* value), and conversely a
well-designed, intent-driven test suite can catch real bugs without ever
being told to aim for a coverage percentage.

This project's `pass_count`/`fail_count`/`test_num` bookkeeping in
`tb/uart_tasks.v`, and the per-category test inventory in Section 3
above, are a **functional coverage summary**: they answer "which
scenarios did we check, and did the design behave correctly for each,"
which is the metric that actually matters for a verification effort, not
"which lines executed." Icarus Verilog does not support SystemVerilog
`covergroup`/`coverpoint` constructs, so no line/toggle/branch code-
coverage tool is used here; if code coverage were desired as a secondary
sanity check (e.g. "did we ever accidentally leave the `S_BREAK` state
completely unreached"), a tool like Verilator's `--coverage` flag could
be layered on top of this same RTL and testbench structure without
requiring any RTL changes, since nothing here depends on Icarus-specific
behavior.

## 7. Simulation instructions

```sh
# Full regression, every testbench, one pass/fail summary (recommended):
make regression

# Individual testbenches:
make sim_top       # tb/uart_tb.v      (1407 checks: 3-parity-mode loopback)
make sim_tx        # tb/uart_tx_tb.v   (228 checks: TX + parity-bit line-level capture)
make sim_rx        # tb/uart_rx_tb.v   (54 checks: fault injection, break detection)
make sim_vectors   # tb/uart_vectors_tb.v (Python-vector regression; regenerates vectors first)

# Regenerate the Python reference-model vector file with a different seed/count:
make vectors SEED=999 NVEC=500

# Waveform inspection (VCD), any testbench:
make waves TB=uart_rx_tb
gtkwave build/uart_rx_tb_waves.out.vcd    # or wherever your viewer opens it; see below

make clean          # remove build/ artifacts
```

### What to look at in a waveform, and why

`make waves TB=<name>` compiles that testbench with a `WAVES` macro
defined, which enables a guarded `$dumpfile`/`$dumpvars` block already
present in each testbench (off by default, so ordinary regression runs
don't pay the small-but-nonzero cost of dumping every signal on every
run). Signals worth looking at, and what they tell you:

- **`tx` / `rx`** (the serial line(s)): the ground truth of what was
  actually sent -- compare bit widths and values directly against what a
  test expected.
- **`baud_tick` / `baud_restart`** (inside `uart_tx`'s instance): confirms
  the restart-then-tick handshake described in `docs/architecture.md`
  Section 7 -- `baud_restart` should pulse exactly once, on the
  `IDLE`->`START` transition, and every subsequent `baud_tick` should be
  exactly `CLKS_PER_BIT` cycles apart.
- **FSM `state`** (both `uart_tx` and `uart_rx`): visualize as an
  enumerated/state signal if your viewer supports it; confirms the
  IDLE->START->DATA->[PARITY]->STOP sequence and, for RX, the
  BREAK-state excursion during a break condition.
- **`bit_index`**: should count `0` to `DATA_BITS-1` once per frame, reset
  at the start of the next.
- **the parity bit's own segment on the line, plus `parity_error`**: the
  most direct way to visually confirm the EVEN/ODD calculation from
  `docs/architecture.md` Section 4.2 against a specific byte value.
- **`low_run_count`, `break_detected`** (inside `uart_rx`): watch
  `low_run_count` ramp up during a held-low condition and confirm
  `break_detected` asserts at exactly `BREAK_THRESHOLD_CYCLES` and clears
  the instant the line returns high.

## 8. Future improvements

- **FIFOs** for TX and RX, explicitly deferred by this phase's scope, to
  decouple the byte-at-a-time interface from a bursty producer/consumer.
- **Fractional (accumulator-based) baud-rate generation**, if a specific
  target clock/baud combination is ever identified where the integer-
  division error calculated in `docs/architecture.md` Section 7 is no
  longer negligible.
- **Configurable stop-bit count** (1 vs. 1.5 vs. 2), building on the
  existing `DATA_BITS`-style parameterization pattern.
- **Independent TX/RX reset domains**, if a real use case ever needs to
  reset one half of the link without disturbing the other.
- **Sub-bit-period oversampling** (e.g. 3x or 8x oversampling with
  majority-vote sampling, rather than a single center sample), which
  would let the receiver distinguish "a stop bit that was briefly low
  then recovered" from "a stop bit that was genuinely low throughout,"
  closing the "known limitation" noted in Section 5, and would also
  improve robustness against line noise generally.
- **Code coverage via Verilator**, as a secondary sanity check layered on
  top of the existing functional test suite (see Section 6), to catch any
  RTL branch that the current, intent-driven test inventory happens not
  to exercise.
